## Why Does This Project Need a 3D Printed Engine?

The project title is "AI-Enhanced Thrust Reverser Deployment Monitoring System Using Digital Twin Technology." The key phrase is "digital twin": by definition, a digital twin is a virtual replica of a physical system. Without a physical counterpart, the virtual system is a simulation rather than a digital twin. The 3D printed engine provides the physical half of that relationship.

Beyond completing the digital twin concept, a physical prototype provides independent validation of the AI classifier. The current system was trained and tested on data generated by the NX MCD simulation. While cross-validation and robustness testing mitigate overfitting, there is still a fundamental limitation: the test data comes from the same source as the training data. A physical model introduces real mechanical play from servo motors, real electrical noise from potentiometers and real timing jitter from Arduino sampling. If the classifier can handle these real-world imperfections, that is a significantly stronger validation claim.

## How Does This Relate to the Project Proposal?

The project proposal states the objective of creating a "functional digital twin" and demonstrating "real-time fault detection." The Cadly Electric TurboFan model directly addresses both objectives. It features functional reverse thrusting: the internal blocker doors open and close via an MG996R servo actuator, which is exactly the thrust reverser deployment mechanism the digital twin simulates. An Arduino Nano controls the deployment scenarios and reads position data from a 10k ohm linear potentiometer, providing the same type of sensor feedback the virtual system uses.

The physical prototype is a standalone system. The deployment scenarios are programmed directly in Arduino code rather than controlled through the PLC or Python pipeline. This keeps the implementation focused and avoids the complexity of bridging Arduino hardware into the existing PLCSIM Advanced communication architecture. The seven fault scenarios (Normal, Asymmetric Speed, Delayed Deployment, Incomplete Deployment, Oscillating Deployment, Stall Deployment and Combined Fault) are each coded as distinct servo movement profiles that the Arduino executes on command.

## Will the Components Fit?

The Cadly model was specifically designed to house all of the recommended electronics. The Arduino Nano, MG996R servo, potentiometer, ESC and brushless motor all have designated mounting locations within the assembly. The designer provides a photographic build guide (v1.9) that has been followed by over 300 builders. This is not a display model with electronics retrofitted in. It was engineered from the start to be a functional, instrumented assembly.

## Can the Model Be Scaled Down?

The model can be scaled in any slicer software, but scaling down is not recommended. The electronic components (Arduino Nano, MG996R servo, potentiometer) are fixed physical sizes and the internal mounting points are designed for 100% scale. Scaling down would require redesigning these mounting features to fit the same hardware in a smaller cavity, which defeats the purpose of using a proven, builder-tested design.

The designer specifies a minimum print plate size of 250x210x200mm. The university has a large-format 3D printer that exceeds this requirement, so all parts can be printed at the original scale without splitting or modification.

## Testing and Validation Before Printing

Before any filament is used, the electronics can be validated independently on a breadboard. The servo is tested for range and repeatability to confirm it can produce consistent deployment movements. The potentiometer is calibrated against known positions to verify it provides stable, accurate feedback. The Arduino code for each deployment scenario is written and tested on the breadboard setup to confirm the servo responds correctly and the potentiometer readings match expected deployment profiles. This proves the physical control system works as intended before a single part is printed.

## What is Next

With the justification established and the STL files sent for review, the next step is sourcing the hardware components, checking what the university labs already have in stock and purchasing the remaining items. The pre-print breadboard validation can begin as soon as the Arduino, servo and potentiometer are available, running in parallel with the 3D printing timeline.
